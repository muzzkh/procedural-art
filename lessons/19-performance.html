Lesson 19

Performance

Scale changes what a system can express. A flock of two hundred is a diagram, and a flock of twenty thousand is a murmuration. This lesson is about getting there: finding what is slow, and the handful of techniques that make sketches ten or a hundred times faster.

Measure first

The first rule of performance work is that your guess about what is slow is probably wrong. Measure before changing anything.

A smooth animation has 16.7 milliseconds per frame at 60 frames a second. Everything, computing and drawing, must fit in that. The simplest measurement is a stopwatch round a piece of code:

const start = performance.now();
update();
const updateMs = performance.now() - start;

For a fuller picture, use the browser's own profiler. Press F12, open the Performance tab, press record, let the sketch run for a few seconds, and stop. The chart shows, for every frame, which functions took the time. Look for the widest bars. Nearly always one or two functions account for most of it, and those are the only ones worth touching.

Spatial hashing

Boids, packing, differential growth and cloth collisions all ask the same question: what is near this point? The obvious way is to check every other point, which makes the work grow with the square of the count. Two thousand points need four million checks per frame. Twenty thousand need four hundred million.

Almost all of those checks are wasted on points that are nowhere near. A spatial hash avoids them. Lay a coarse grid over the canvas, with cells as wide as the distance you care about, and drop each point into its cell. A point's neighbours can then only be in its own cell and the eight around it.

The example runs the same simulation both ways and times it. Raise the particle count with the grid off, and watch the time climb steeply. Then turn the grid on.

Typed arrays and avoiding garbage

JavaScript makes it easy to give every particle its own object: { x, y, vx, vy }. For large counts there is a leaner layout. A typed array, such as Float32Array, is a block of raw numbers with no object around each one. Keep one array per property, so that particle i is x[i], y[i], vx[i], vy[i]. The numbers sit side by side in memory, which processors handle very efficiently, and nothing is created or thrown away as the sketch runs.

The second half of this is garbage. Every object or array you create must eventually be cleaned up by the browser, and the cleaning happens in pauses that show as stutter. Code that makes a small temporary object for every particle on every frame, a very natural thing to write, creates millions of them a second.

The example times three versions of the same update on your machine. The numbers vary between browsers and computers, which is the point: it measures, it does not assume.

Drawing fast

Often the drawing costs more than the computing. Three habits help most:

  • Batch. One beginPath, many moveTo and lineTo calls, one stroke. A thousand segments in a single path draw far faster than a thousand separate strokes. Group by colour and line width, since those cannot change within a path.
  • Write pixels directly. For hundreds of thousands of points, set values in an ImageData array and put it on the canvas once, as the pixel examples in this course do.
  • Cache. Anything that does not change, such as a background, a texture, or a finished layer, is drawn once to a hidden canvas and copied each frame with drawImage.

Web workers

JavaScript in a page runs on one thread, which also handles scrolling, clicks and drawing. A calculation that takes two seconds freezes the whole page for two seconds. A web worker is a second thread. You send it a job as a message, it computes without blocking anything, and it sends results back as messages.

Workers suit work that is heavy but does not need to finish within a frame: rendering a large image, solving a big Wave Function Collapse, growing a structure, packing a hundred thousand circles. They cannot touch the page or the canvas directly. They receive data and return data.

Here a worker renders a detailed fractal one row at a time. The small square keeps spinning throughout, which shows that the page has stayed responsive.

The graphics card

The largest step up is to move the work onto the GPU, which runs the same small program on enormous numbers of elements at once. Lesson 9 did this for pixels. It works for particles too.

The simplest GPU particle system has no stored state at all. Each particle is given a few fixed numbers when it is created, and a vertex shader computes where it is from those numbers and the current time. JavaScript does nothing per particle while it runs. That restricts you to motion that can be written as a formula of time, as in Lesson 15, but within that limit a few hundred thousand particles cost almost nothing.

Particles that interact, or that follow a simulation, need their positions stored and updated on the GPU as well. That is done by keeping positions in a texture and updating it with a fragment shader each frame, a technique known as GPU particle simulation, or with the transform feedback and compute features of newer graphics interfaces. It is a substantial step beyond this lesson, and three.js (see that section) removes much of the set-up.

The last row matters most. The cheapest optimisation is often to notice that the picture does not need what you are computing.

Key ideas

  • Measure before optimising. One or two functions usually hold nearly all the time.
  • A frame has 16.7 milliseconds.
  • A spatial grid turns "check everything" into "check the neighbourhood".
  • Typed arrays and reused objects avoid the pauses caused by garbage.
  • Batch drawing calls, write pixels directly, and cache what does not change.
  • Workers keep the page responsive during heavy work. The GPU handles the largest counts.

Common mistakes

  • Optimising code that was never the bottleneck, and making it harder to read for nothing.
  • Timing with the developer tools open and drawing conclusions from the absolute numbers. They slow things down. Compare before and after under the same conditions.
  • Making the code fast before the picture is good. Find the image first.

Challenge 19

Ten Times Faster

The starter file contains a working sketch that is deliberately, badly slow. Make it at least ten times faster without changing what it draws, then use the speed you have won to make it better.

Requirements

  • Measure first. Record the starting time per frame, and use the browser's profiler to find the two most expensive parts. Write both down in a comment before changing anything.
  • The optimised sketch draws the same picture for the same seed. Keep the original function so that you can compare.
  • At least ten times faster per frame at the original particle count, measured the same way.
  • At least three different techniques from this lesson, each noted in a comment with the time it saved.
  • Then raise the count until the frame time is back near 16 milliseconds, and report how many particles that is.
  • A short write-up, in comments: what was slow, what you changed, and what surprised you.

Hints

  • Change one thing at a time and measure after each. Some changes will do nothing, and that is useful to know.
  • The starter has at least four separate problems. They are not equally important.
  • To check that the picture is unchanged, draw old and new side by side with the same seed.

Stretch goals

  • A hundred times faster.
  • Move the simulation into a web worker.
  • Rebuild it on the GPU.

You are done when

  • Your measurements show the tenfold gain, and you can say which change gave most of it.
  • The larger version is a better picture, not just a busier one.
