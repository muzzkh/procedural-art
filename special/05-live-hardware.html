Special Topic 5

Live Hardware

Generative work does not have to stay on a monitor. It can run on a strip of lights, respond to a body in front of a camera, or be projected onto a building. This page covers addressable LEDs, cameras and pose tracking, and projection mapping.

What was and was not tested. The three live examples on this page run in the browser and were checked like every other example in the course, with one exception: the camera example could only be checked up to the point where it asks for a camera, since none was available.

The code listings for microcontrollers, the Web Serial connection and pose tracking were not run. They are written from the documented interfaces of those libraries, and they are complete, but treat them as a starting point and expect to adjust names and version numbers.

Designing for hardware

Moving to physical output changes the constraints, much as fabrication did in Special Topic 3.

On a monitorOn hardware
Millions of pixelsA few hundred lights, or a projector fighting daylight
A fast processor and plenty of memoryA microcontroller with a few kilobytes
Decimal numbers everywhereOften whole numbers from 0 to 255
It runs while you watchIt runs for weeks, unattended, and must recover from power cuts
Nobody is harmed by a bugPower, heat and bright flashing light are real concerns

The good news is that the techniques survive almost unchanged. Noise, palettes, cellular automata and particle systems all work at sixteen pixels wide. In fact low resolution flatters them: a noise field that looks bland on a screen is mesmerising on a wall of lights.

Addressable LEDs

An addressable LED strip is a chain of lights in which each one can be set to its own colour. The common types are known by their chip names, WS2812B (sold as NeoPixel) and APA102 (DotStar). A strip is wired to a small microcontroller, such as an Arduino, an ESP32 or a Raspberry Pi Pico, which sends the colours down the chain many times a second.

A strip is a one-dimensional image. A strip folded back and forth across a panel is a two-dimensional one, and all you need is a function from row and column to position along the strip.

Prototype in the browser first

Because the hardware is slow to reprogram, design the pattern on a simulated strip or matrix, at the real resolution, and only then move it across. The simulator below draws a 16 × 16 panel as glowing dots, and estimates the electrical current the pattern would draw, which is the number you need for choosing a power supply.

The same pattern on a microcontroller

This is the equivalent program for an Arduino-compatible board using the FastLED library, which includes fast whole-number noise and palette functions designed for exactly this.

// Arduino C++ with the FastLED library.  NOT RUN as part of preparing this course.
#include <FastLED.h>

#define DATA_PIN    5
#define COLS        16
#define ROWS        16
#define NUM_LEDS    (COLS * ROWS)
#define BRIGHTNESS  60            // out of 255. keep it low while testing

CRGB leds[NUM_LEDS];

// Panels are usually wired in a zigzag: every other row runs backwards.
uint16_t ledIndex(uint8_t x, uint8_t y) {
  return (y % 2 == 0) ? (y * COLS + x) : (y * COLS + (COLS - 1 - x));
}

void setup() {
  FastLED.addLeds<WS2812B, DATA_PIN, GRB>(leds, NUM_LEDS);
  FastLED.setBrightness(BRIGHTNESS);
  FastLED.setMaxPowerInVoltsAndMilliamps(5, 2000);    // never draw more than 2 A, whatever the pattern asks
}

void loop() {
  uint16_t t = millis() / 8;
  for (uint8_t y = 0; y < ROWS; y++) {
    for (uint8_t x = 0; x < COLS; x++) {
      uint8_t n = inoise8(x * 40, y * 40, t);                 // noise, 0 to 255
      leds[ledIndex(x, y)] = ColorFromPalette(OceanColors_p, n);
    }
  }
  FastLED.show();
  FastLED.delay(16);                                          // about 60 frames a second
}

And the same idea in MicroPython, for a Raspberry Pi Pico or ESP32, using its built-in NeoPixel driver:

# MicroPython.  NOT RUN as part of preparing this course.
import math, time
from machine import Pin
from neopixel import NeoPixel

COUNT = 60
strip = NeoPixel(Pin(5), COUNT)

def wheel(position, level):
    """A colour from a position 0..1 round the hue circle, at a brightness 0..1."""
    r = 0.5 + 0.5 * math.cos(2 * math.pi * position)
    g = 0.5 + 0.5 * math.cos(2 * math.pi * (position + 0.33))
    b = 0.5 + 0.5 * math.cos(2 * math.pi * (position + 0.67))
    return (int(r * 255 * level), int(g * 255 * level), int(b * 255 * level))

t = 0.0
while True:
    for i in range(COUNT):
        wave = 0.5 + 0.5 * math.sin(i * 0.25 + t)          # a travelling wave of brightness
        strip[i] = wheel(i / COUNT + t * 0.05, 0.2 * wave)
    strip.write()
    t += 0.08
    time.sleep_ms(20)

That wheel function is the cosine palette of Lesson 9.

Power and safety

  • Each LED can draw about 60 milliamps at full white. A 16 × 16 panel at full brightness needs over 15 amps. Size the power supply for the worst case, or cap the brightness in software as the listing does.
  • Never power more than a few LEDs from the microcontroller's own pins. Use a separate 5 volt supply and join its ground to the board's ground.
  • Thin wires carrying several amps get hot. Feed power into long strips at both ends.
  • Bright, fast flashing can trigger seizures in people with photosensitive epilepsy. Avoid full-field flashes faster than about three per second, and be especially careful with red.

Driving hardware from the browser

You can also keep the generative code on a computer and send colours to the board over USB. Chrome and Edge provide a Web Serial interface for this. It needs a click from the user before it will connect.

// Browser JavaScript (Chrome or Edge).  NOT RUN as part of preparing this course.
let writer = null;

connectButton.addEventListener('click', async () => {
  const port = await navigator.serial.requestPort();        // the browser shows a list of devices
  await port.open({ baudRate: 115200 });
  writer = port.writable.getWriter();
});

// Send one frame: a marker byte, then red, green, blue for every LED.
async function sendFrame(colours) {                          // colours: [[r, g, b], ...] each 0 to 255
  if (!writer) return;
  const bytes = new Uint8Array(1 + colours.length * 3);
  bytes[0] = 255;                                            // "start of frame". keep colour values below 255
  colours.forEach(([r, g, b], i) => {
    bytes[1 + i * 3] = Math.min(r, 254);
    bytes[2 + i * 3] = Math.min(g, 254);
    bytes[3 + i * 3] = Math.min(b, 254);
  });
  await writer.write(bytes);
}

The board runs a short program that waits for the marker byte, reads three bytes per LED, and shows them. For larger installations the same idea runs over a network, using the Art-Net or sACN lighting protocols, and ready-made firmware such as WLED turns an ESP32 into a controller that accepts them.

Cameras

A camera turns the space in front of a piece into data. The browser gives access to it with one call, after asking the visitor's permission. Each video frame can be drawn onto a hidden canvas and read as pixels, exactly like a still image in Lesson 13.

The most robust thing to measure is motion: the difference between this frame and the last. It needs no calibration and works in almost any light. Shrink the frame to a coarse grid first. A grid of 80 by 60 is ample, far cheaper, and less sensitive to camera noise.

Pose tracking

Machine-learning models can now find a person's joints, hands or face in a video frame, in real time, in a browser. Google's MediaPipe library is the usual way to do it. It returns a list of landmarks, 33 for a body, each with a position between 0 and 1. From then on they are ordinary points: attractors, emitters, the ends of a rope, the corners of a shape.

// Browser JavaScript, in a <script type="module">.  NOT RUN as part of preparing this course.
// Check the current version number and model address in the MediaPipe documentation.
import { PoseLandmarker, FilesetResolver } from 'https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@0.10.14';

const files = await FilesetResolver.forVisionTasks('https://cdn.jsdelivr.net/npm/@mediapipe/tasks-vision@0.10.14/wasm');
const tracker = await PoseLandmarker.createFromOptions(files, {
  baseOptions: {
    modelAssetPath: 'https://storage.googleapis.com/mediapipe-models/pose_landmarker/pose_landmarker_lite/float16/1/pose_landmarker_lite.task',
    delegate: 'GPU',
  },
  runningMode: 'VIDEO',
  numPoses: 1,
});

const video = document.querySelector('video');
video.srcObject = await navigator.mediaDevices.getUserMedia({ video: true });
await video.play();

function frame() {
  const result = tracker.detectForVideo(video, performance.now());
  if (result.landmarks.length > 0) {
    const body = result.landmarks[0];                  // 33 points, each { x, y, z } from 0 to 1
    const leftWrist = body[15], rightWrist = body[16];
    // from here it is ordinary procedural code: use the points as inputs
    emitParticlesAt((1 - leftWrist.x) * canvas.width, leftWrist.y * canvas.height);
    emitParticlesAt((1 - rightWrist.x) * canvas.width, rightWrist.y * canvas.height);
  }
  requestAnimationFrame(frame);
}
frame();

Tracking is never perfect. Smooth the landmark positions over a few frames, as in Special Topic 1, and design the piece so that a lost or jumping point degrades it gracefully instead of breaking it.

Cameras and people

  • Say clearly that a camera is in use, and why.
  • Process the video where it is, and do not store or send it unless people have agreed.
  • An abstract response to motion is usually more inviting than showing people their own image.
  • Test with different bodies, clothing, skin tones and lighting. Tracking models do not work equally well for everyone.

Projection mapping

A projector pointed at a wall, a sculpture or a building turns that surface into a screen. The difficulty is that the projector is hardly ever square-on, so a rectangle of light lands as a skewed four-sided shape. Projection mapping is the business of warping the image in advance so that it lands where you want.

The basic tool is the corner pin. You drag the four corners of your image until they sit on the four corners of the real surface, and the software stretches everything in between to match. Drag the handles below. The pattern is drawn by dividing the shape into a grid of small cells and placing each cell's corners by interpolating between the four handles, which is lerp applied twice.

This two-way interpolation is simple, and close enough for small corrections. A true perspective correction uses a slightly different mapping, a homography, which keeps straight lines straight across the whole surface. In a web page the easy way to get one is a CSS transform: matrix3d(…) on the canvas element. For complex shapes, the surface is divided into several quads or a mesh, each pinned separately.

Practicalities

  • Darkness and brightness. Projection only works in dim light. A projector's brightness is given in lumens: a few thousand is enough for a dark room, and building-scale work needs tens of thousands.
  • Black is the absence of light. A projector cannot project black. Design with light on a dark ground, and use black as "nothing here".
  • The surface is part of the image. Texture and colour show through. Edges, windows and ledges are things to align with, and the most effective pieces use the architecture instead of ignoring it.
  • Tools. MadMapper, Resolume and TouchDesigner are the usual software. A browser in full-screen mode on the projector's display works for simple pieces.
  • Permission. Projecting on buildings you do not own usually needs it.

Key ideas

  • The course's techniques work at very low resolution, and often look better there.
  • Design LED patterns in a simulator at the real resolution, then port them.
  • Budget for power: about 60 milliamps per LED at full white, and cap brightness in software.
  • From a camera, motion between frames is the most dependable signal.
  • Pose tracking returns points. After that it is ordinary procedural code.
  • A corner pin warps an image onto a surface by interpolating between four dragged corners.

Special challenge 5

A Piece for a Place

Design a generative piece for a specific physical setting, real or imagined: a strip of lights on a staircase, a panel in a window, a projection on a particular wall. Build it as far as you can without the hardware, in a simulator that respects the hardware's limits.

Requirements

  • A written description of the place: where it is, how far away people stand, how bright the surroundings are, and what the hardware would be.
  • A simulator at the true resolution: the actual number and layout of LEDs, or the actual shape of the projection surface with a corner pin.
  • Colours handled as whole numbers from 0 to 255, and for LEDs a current estimate with a software limit.
  • At least three patterns the piece moves between, with smooth transitions.
  • It reacts to one live input: motion from a camera, sound level, the time of day, or the pointer standing in for a sensor.
  • It could run unattended: no state that grows for ever, and a sensible start after a restart.
  • No full-field flashing faster than three times a second.

Hints

  • Write the pattern as a function from LED number (or position) and time to a colour. That function is what you would port.
  • Squint at the simulator from across the room. That is closer to how the real thing will read.
  • Keep overall brightness low. Lights look far brighter in a real dark room than on a monitor.

Stretch goals

  • If you have the hardware: port it, and note what had to change.
  • Send frames from the browser over Web Serial.
  • Use pose tracking so that the piece follows one person's hands.

You are done when

  • Someone reading your description and watching the simulator can picture the installation.
  • You could hand the pattern function to someone with the hardware and they could build it.
