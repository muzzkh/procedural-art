Special Topic 9

Project Workflow

A generative practice produces thousands of files and hundreds of small programs, and the one you need is always the one you cannot find or cannot reproduce. This page is about the habits that prevent that: version control, saving the recipe with every output, and building a library of your own.

The three things that go wrong

  1. "I can't make that image again." The seed was not recorded, or the code has changed since.
  2. "It worked yesterday." A change broke something and there is no way back.
  3. "I've written this before." The same helper functions are retyped, slightly differently, in every sketch.

Each has a standard cure, and none takes more than a few minutes to set up.

Save the recipe with every output

An output of a generative system is fully described by three things: the code, the seed, and the parameters. If you keep all three, the image can always be regenerated, at any size. If you lose one, it is gone.

The habit that makes this automatic:

  • Put every adjustable value in one object, not scattered through the code.
  • Whenever you save an image, save that object beside it as a small text file, with the same file name.
  • Put the seed and a short fingerprint of the parameters in the file name, so that files identify themselves and never overwrite each other.
  • Include the code version in the object.

The example does all four. Click the canvas to save the image and its recipe together.

To bring an old output back, read its recipe file and pass it to the same render function. Two refinements are worth adding to your own sketches. Put the parameters in the page address as well (Special Topic 1), so that any state can be shared as a link. And make "save" a single key, so that you press it whenever something catches your eye, without deciding whether it is worth it.

Version control

Version control records the state of your files each time you tell it to, and lets you return to any earlier state. The standard tool is Git. It is free, it works on your own computer with no account, and for a single artist five commands are enough.

git init                                  # once, in the project folder: start recording
git add .                                 # choose what to include: here, everything changed
git commit -m "Flow field with margins"   # record the current state, with a note
git log --oneline                         # list the recorded states
git checkout a1b2c3d                      # go back to the state called a1b2c3d   (git switch - to return)

These are standard commands. They were not run as part of preparing this page.

How to use it for sketches

  • Commit whenever something works or looks interesting, however small. A commit is a save point you can return to. Many small ones are better than a few large ones.
  • Write the note for your future self: what changed, in a few words. "Thicker lines near centre", not "update".
  • Commit before every experiment. Then no change is risky: if it fails, go back.
  • Tag the version behind every finished piece: git tag tidewater-v1. The code version in a recipe file should name a tag or commit, which makes the recipe complete.
  • Keep outputs out of it. List your output folder in a file called .gitignore. Git is for code and small text files. Thousands of images make it slow, and they can be regenerated.
  • Put a copy elsewhere. Pushing the repository to a hosting service such as GitHub is also your off-site backup of the code.

A folder layout that scales

procedural/
  lib/                     your own library: the code every sketch shares
  sketches/
    2026-11-flow-margins/  one folder per sketch, dated
      index.html
      sketch.js
      notes.md             what you were trying, what you learned
  projects/
    tidewater/             finished or serious work, each its own Git repository
      src/
      lib/                 a COPY of the library as it was when the piece was made
      output/              images and their recipe files (not in Git)
      README.md            statement, edition details, how to run it
  reference/               images and links you are studying

The distinction between sketches and projects matters. A sketch is disposable: date it, keep it, never tidy it. When one turns into real work, move it to a project of its own.

A library of your own

This course's PA is a personal library: seeded randomness, noise, colour helpers, a few algorithms. Yours will end up different, because it will hold the things you reach for. Building it is one of the best investments in a practice, since each new piece starts from everything you have already solved.

  • Extract on the third use. The first time you write something, just write it. The second time, copy it. The third time, move it into the library.
  • Small functions that do one thing and take everything they need as arguments. No hidden dependence on a global canvas or a global random generator.
  • Your defaults belong here: your palettes, your margins, your grain, your line quality. This is where a style becomes reusable.
  • Document with one line and one example per function. You will forget.
  • Never change what an existing function returns for a given input. If you improve noise, every old piece that used it changes. Add a new function instead, or bump the version.
  • Freeze the library into finished projects. Copy the version you used into the project's own folder. The piece then depends on nothing that can change under it.

Checking that nothing has changed

How do you know an edit to your library has not altered old work? Compare outputs before and after. Doing that by eye is unreliable, so reduce each output to a short fingerprint and compare those. A fingerprint is a hash, as in Lesson 2: any change to the data, however small, gives a different number.

Fingerprint the data a generator produces, its list of positions and sizes, not the pixels, because the same drawing can differ by a hair between browsers. Record the fingerprints of a few seeds. From then on, a check takes a moment and catches any accidental change. Programmers call this a snapshot test.

Daily practice

  • Sketch often and small. Twenty minutes with a narrow question beats a weekend with a vague one. Many generative artists keep a daily habit for exactly this reason.
  • Keep notes. One line per session: what you tried, what happened. Ideas that failed today are raw material in a year.
  • Save surprises immediately, with their recipe. You will not find that seed again.
  • Review monthly. Look through the saved folder. Promote the best to projects, and notice what you keep returning to.
  • Back up in three places: the working copy, a second drive, and somewhere off-site. Code goes to a hosting service. Finished master files go to cloud storage as well.
  • Finish. Give things titles, export them, record them. Finishing is a skill, and it is only learned by doing it.

Key ideas

  • Code, seed and parameters together are the recipe for an output. Keep all three, always.
  • One parameters object, saved beside every image under the same name.
  • Commit small and often. Commit before experiments. Tag what finished pieces were made with.
  • Sketches are disposable and dated. Projects are separate and self-contained.
  • Extract shared code into your own library on the third use, and freeze a copy into finished work.
  • Fingerprint a generator's data to catch accidental changes.

Special challenge 9

A Workshop of Your Own

Set up the working environment you will use from now on, and prove it by moving one of your course pieces into it.

Requirements

  • A folder layout with separate places for the library, dated sketches and projects, under Git, with outputs ignored.
  • A personal library file of at least eight functions that you wrote or adapted during this course, each with a one-line description. At least three should express your own preferences: a palette, a margin rule, a texture.
  • A sketch template: the file you copy to begin anything new. It has one parameters object, a seeded generator, a key that saves the image together with its recipe, and parameters readable from the page address.
  • A loader: given a saved recipe file, the template reproduces the image exactly.
  • A fingerprint check for at least two library functions, with recorded values.
  • One earlier challenge piece moved into a project on the new structure, with a frozen copy of the library, a README, and a tagged commit.
  • At least ten commits with notes that say what changed.

Hints

  • Build the template first and use it for everything else in this challenge.
  • For the loader, a file picker reading the recipe with JSON.parse is enough.
  • When you record fingerprints, look at the outputs first. A fingerprint only proves that nothing changed, not that it was right to begin with.

You are done when

  • You can start a new sketch in under a minute.
  • You can pick any image from your output folder and regenerate it from its recipe.
  • You would not be afraid to try a risky change.

References and further reading

The sources for this page, and other places that cover the same ground.

  • Scott Chacon and Ben Straub, Pro Git, 2nd edition, Apress, 2014. Free to read online. The standard book on version control.
  • Matt DesLauriers, canvas-sketch. A framework built around the habits of this lesson: seeds, exports and print sizes.
  • Geir Kjetil Sandve, Anton Nekrutenko, James Taylor and Eivind Hovig, “Ten Simple Rules for Reproducible Computational Research”, PLOS Computational Biology, 2013. Saving the recipe, as scientists state it.
  • Tom Preston-Werner, Semantic Versioning. A convention for numbering versions of a library.
  • Andrew Hunt and David Thomas, The Pragmatic Programmer, Addison-Wesley, 1999. Working habits for anyone who writes code.
