Shaders 4

Memory and Post-processing

A shader forgets everything between frames. Give it one thing to remember, the picture it drew last time, and it can leave trails, grow patterns and run whole simulations on the graphics card. This lesson covers that one idea, and then the family of effects that treat a finished picture as raw material.

One texture of memory

Shaders 1 listed a shader's restrictions: no memory, no neighbours. Both are lifted by a single arrangement. The shader draws into a hidden image instead of onto the screen. On the next frame that image is handed back to the shader as a texture, an image it can read at any position. So the shader can now ask "what was at this pixel last frame?", which is memory, and "what was at the pixel next to it?", which is neighbours.

It cannot read and write the same image at once, so there are two, and they swap roles every frame. This is called ping-pong. It is exactly the pair of arrays, A and A2, that every simulation in Lesson 8 used.

In these examples the previous frame is the uniform u_prev. You read it with texture2D(u_prev, uv), where uv runs from 0 to 1 across the canvas, and get back the four numbers that were stored there. Two more uniforms help: u_frame counts the frames since the example started, so that the first one can set things up, and u_down is 1.0 while the mouse button is held.

Trails

The simplest use: read the old colour, fade it slightly, and draw today's content on top. Anything that moves leaves a trail whose length is set by the fade. Hold the mouse button and draw.

Reading from somewhere else

Nothing says a pixel must read its own old value. If every pixel reads from a position slightly nearer the centre, the old picture is copied outward a little each frame and appears to grow. Add a small rotation and it spirals. This is video feedback, the effect of pointing a camera at its own monitor, and it produces a great deal from very little: the only new content below is one small ring circling the pointer.

State is not a picture: update and display

In the last two examples the remembered image and the picture you saw were the same thing. For a simulation they should be separate. What must be remembered is the state, such as whether a cell is alive, or the amounts of two chemicals, stored as plain numbers in the red and green channels. What you want to see is a rendering of that state, with colour and lighting that must not leak back into it.

So a simulation shader has two parts. In these examples they are two functions in the same listing, in place of main:

  • void update() reads the old state from u_prev and writes the new state.
  • void display() reads the state that was just written, also from u_prev, and writes the colour that appears on screen.

The first simulation is Conway's Game of Life from Lesson 8. Each cell is drawn six pixels across, so the shader first works out which cell the pixel belongs to, and all the pixels of a cell reach the same answer. The red channel holds alive or dead. The green channel counts how long a cell has lived, purely so that display can colour by age.

Reaction and diffusion at full speed

The Gray–Scott system of Lesson 8 and Textures 3 is an ideal fit. Its rule reads the cell and its eight neighbours and nothing else. In JavaScript a grid of 200 by 200 was the comfortable limit. Here every pixel of the canvas is a cell, and the simulation still runs eight steps every frame.

Three details are worth noticing in the listing.

  • The feed rate rises from left to right and the kill rate from bottom to top, so the canvas is a map of every pattern the system can make. Find the regions of spots, stripes and mazes, and the region where nothing survives.
  • The state is two amounts that change by tiny fractions each step. Ordinary image memory holds only 256 levels per channel, which is too coarse, so the examples use decimal ("float") textures wherever the graphics card allows it.
  • display treats the amount of the second chemical as a height and lights it, exactly as in Textures 4. The simulation knows nothing about that.

The same structure runs fluids, sand, erosion, slime moulds and flocking fields. Lesson 19 pointed at the graphics card as the last step in making a simulation fast. This is that step.

Post-processing

A post-process is a shader whose input is a finished picture. It does not know or care how the picture was made. Film and games run a chain of them over every frame, and a small number of them account for most of the "look" of a piece. In the example the picture comes from a function, scene(p), so that an effect which needs the picture at a different position can simply call it again. With a stored picture you would read a texture instead.

Chromatic aberration
A lens bends red and blue light by slightly different amounts. Read the red channel a little further from the centre and the blue a little nearer.
Vignette
Darken toward the corners. It holds the eye in the middle of the frame.
Scanlines
Darken every third row of pixels, as on an old screen.
Grain
Add a small random amount to every pixel, different each frame. It hides banding in smooth gradients (Lesson 11) and takes the plastic cleanness off a render.
Tone curve
Pass each channel through an S-shaped curve to raise the contrast (Maths 1).

The order matters. Grain goes last, because grain that is then given more contrast becomes far too strong. Aberration goes first, because it needs the untouched picture. Comment the five effects out one at a time and see how much each contributes.

Fewer pixels, fewer colours

The other family of post-processes throws information away on purpose. Two reductions give the look of early computer graphics: large square pixels, and a palette of a few colours with ordered dithering (Lesson 13) to suggest the tones in between.

  • Large pixels. Find which block the pixel is in with floor, and evaluate the picture once, at the middle of the block. Every pixel in the block gets the same answer.
  • Ordered dithering. Before rounding a brightness down to the nearest of four levels, add a threshold that depends on the block's position in a repeating four-by-four pattern. Lesson 13 stored that pattern in a table. A shader can compute it from the bits of the position.

Key ideas

  • Handing a shader its own previous frame as a texture gives it memory and neighbours.
  • Two images take turns: one is read while the other is written.
  • Fading the old frame leaves trails. Reading it from a shifted position makes feedback.
  • A simulation stores state, not colours. One function updates the state, another displays it.
  • Small changes need decimal textures. Eight bits per channel is too coarse for most simulations.
  • A post-process takes a finished picture as input: aberration, tone curve, vignette, scanlines, grain, in that order.
  • Large pixels are floor of the position. Ordered dithering is a threshold that depends on position.

Common mistakes

  • A fade by multiplication alone. In 8-bit memory it stops a little above black and leaves a permanent ghost. Subtract a small amount as well.
  • Display colours leaking into the state. If the picture changes the simulation, you have written lighting into update.
  • Reading neighbours at the wrong spacing. One pixel is 1.0 / u_res in texture coordinates, not 1.0.
  • Forgetting the first frame. The memory starts empty, so a simulation needs a line that fills it when u_frame is zero.

Shaders challenge 4

A Shader with a Memory

Write a simulation that lives entirely on the graphics card, responds to the pointer, and is displayed with care.

Requirements

  • A state held in the previous-frame texture, with a comment saying what each channel means.
  • An update that reads the pixel and its neighbours. Choose one: a cellular automaton with your own rule, a reaction–diffusion system with parameters that vary across the canvas, falling sand, or a field of your own design.
  • A separate display that adds colour and lighting without changing the state.
  • A defined first frame, and a way to restart.
  • The pointer adds, removes or disturbs something.
  • At least two post-processes applied in display, chosen to suit the subject.

Hints

  • Get the rule working with the plainest possible display first: state shown directly as red and green.
  • If the simulation freezes or blows up, show the state with inspect from Shaders 1.
  • For falling sand, a cell needs to know what is below it and what is above it, and both must agree about who moves. Work it out on paper for two cells first.

Stretch goals

  • Use the blue and alpha channels for a second, slower quantity that influences the first, such as heat or age.
  • Run the state at a quarter of the canvas resolution and display it smoothly at full size.

You are done when

  • It runs for five minutes without settling into a dead or frozen state, or it settles into something worth keeping.
  • Someone who plays with it for a minute can tell you what the pointer does.
